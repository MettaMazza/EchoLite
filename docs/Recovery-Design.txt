ECHOLITE RECOVERY — implemented protocol and remaining acceptance

Implemented: managed sealed SQLite snapshots, independent recovery.guard generation, pre-commit forgetting invalidation, read-only diagnosis, process-lifetime shared core/worker leases, exclusive maintenance, backup-check and backup-restore. This does not close the complete G14 release gate.

Restore protocol:
1. Acquire exclusive state and worker leases before opening live state. Refuse active work rather than stopping it implicitly. Validate the requested ID, independent authority, private managed paths, whole-file checksum, snapshot identity and structural state.
2. Copy the standalone snapshot and its seal into private bounded-buffer preparation. Recheck exact bytes and authority. Before this point live state remains untouched. Failed/orphan preparation is disposable and participates in forgetting cleanup.
3. Durably publish .restore.pending with the selected ID and recovery generation before removing any live WAL/SHM files or replacing memory.sqlite3. While the marker exists, ordinary commands and worker startup refuse to open live state. A malformed marker or mismatched ID/generation fails closed.
4. Retire old sidecars only under exclusion and intent, atomically publish the verified replacement, then run native recovery policy. Pending turns become abandoned; incomplete external execution outcomes are explicitly unknown. Durable completed/failed process results remain readable, with reconstructed receipt provenance where needed. No external operation is run or undone.
5. Record the latest restore timestamp in metadata. A bounded global notice autoloads in subsequent contexts, including projects without pending turns and newly created projects. It distinguishes historical receipts from current external state without storing project content or changing Me. Clear exact response caches while retaining persistent prompt checkpoints and embeddings for ordinary validation/reuse. Commit the recovery audit, regenerate Me.txt, verify live structural health and identity agreement, synchronize files, then durably remove the intent.
6. A retry with the same original backup rebuilds from that retained sealed source and repeats recovery. Seven controlled process-exit boundaries have been tested, including after sidecar retirement, after replacement, around the recovery transaction and before intent clearing.

Forgetting rotates authority before commit and removes managed snapshots/seals plus orphan restore preparation. If cleanup fails, memory deletion does not commit. A crash before commit can invalidate redundancy while retaining live memory; the explicit operation must be retried. This is fail-closed privacy behavior rather than an atomic cross-filesystem transaction or forensic erasure.

Evidence includes seventeen native restore cases, nine read-only health cases, the selected combined native suite and real MiniLM recall/document-vector reuse after native restore. Test generation in the semantic integration fixture is controlled; it is not a live Qwen restore-conversation acceptance run.

A synthetic 2.25 GiB cache backup/restore/forget run now passes with every restored byte verified (recovery-scale-2304mib/report.json). Restore took 9.313 seconds at 14.39 MiB peak native RSS in that single run; the separate full-context model probe was active. This is storage evidence, not model-produced checkpoint reuse.

Remaining: actual model-checkpoint backup/restore and repeated resource/latency measurements, forced disk-full and storage-failure/power-loss recovery, end-to-end live-4B user sessions after restore, broader lifecycle/restore-awareness evaluation, detached external process handling and final release audit. The original selected snapshot, seal and independent authority must remain available during interrupted restoration. Total directory/disk loss and a same-user actor deliberately rewriting all authority are outside this same-directory recovery mechanism.
